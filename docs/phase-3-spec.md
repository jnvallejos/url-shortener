## 3. Persistence Layer

### 3.1 `ApplicationDbContext`

Single context, two `DbSet`s.

```csharp
public sealed class ApplicationDbContext : DbContext
{
    public ApplicationDbContext(DbContextOptions<ApplicationDbContext> options)
        : base(options) { }

    public DbSet<ShortUrl> ShortUrls => Set<ShortUrl>();
    public DbSet<ClickAudit> ClickAudits => Set<ClickAudit>();

    protected override void OnModelCreating(ModelBuilder modelBuilder)
    {
        modelBuilder.ApplyConfigurationsFromAssembly(typeof(ApplicationDbContext).Assembly);
    }
}
```

**Decisions:**
- `DbSet`s expose Domain entities directly. EF Core works with them via configurations (no separate persistence DTOs).
- `ApplyConfigurationsFromAssembly` discovers all `IEntityTypeConfiguration<T>` in the Infrastructure assembly automatically.
- Constructor takes `DbContextOptions<ApplicationDbContext>` (the standard EF Core pattern). The DI extension provides those options.

### 3.2 `ShortUrlConfiguration`

Maps the `ShortUrl` aggregate to a relational schema. The domain model has private setters and value objects; the configuration must teach EF Core how to materialize and persist this without breaking encapsulation.

**Schema:**

```
ShortUrls
- Id            uniqueidentifier primary key
- ShortCode     varchar(7)      not null, unique index
- OriginalUrl   varchar(2048)   not null
- CreatedAt     timestamptz     not null
- ExpiresAt     timestamptz     null
- IsEnabled     boolean         not null
- ClickCount    bigint          not null
```

**Configuration body:**

```csharp
public sealed class ShortUrlConfiguration : IEntityTypeConfiguration<ShortUrl>
{
    public void Configure(EntityTypeBuilder<ShortUrl> builder)
    {
        builder.ToTable("ShortUrls");

        builder.HasKey(s => s.Id);

        builder.Property(s => s.ShortCode)
            .HasConversion(
                code => code.ToString(),
                value => ShortCode.Create(value))
            .HasMaxLength(7)
            .IsRequired();

        builder.HasIndex(s => s.ShortCode).IsUnique();

        builder.Property(s => s.OriginalUrl)
            .HasConversion(
                url => url.ToString(),
                value => OriginalUrl.Create(value))
            .HasMaxLength(2048)
            .IsRequired();

        builder.Property(s => s.CreatedAt).IsRequired();
        builder.Property(s => s.ExpiresAt);
        builder.Property(s => s.IsEnabled).IsRequired();
        builder.Property(s => s.ClickCount).IsRequired();

        builder.Ignore(s => s.DomainEvents);
    }
}
```

**Decisions:**
- **Value object conversion:** `ShortCode` and `OriginalUrl` persist as strings via `HasConversion`. The reverse uses the factory method, so reading from DB validates again — defensive.
- **Unique index on `ShortCode`:** the database is the second line of defense for uniqueness. The Application layer's `ExistsByCodeAsync` is the first; this index protects against races.
- **`DomainEvents` ignored:** it's an in-memory list, not persisted.
- **No private constructor needed in Phase 1:** EF Core can use the existing private constructor reflection-style. If a `[GeneratedRegex]`-style issue arises, a parameterless private constructor will be added to `ShortUrl` and **only then** will Domain be touched (and that decision will be flagged before doing it).

### 3.3 `ClickAuditConfiguration`

```
ClickAudits
- Id              uniqueidentifier primary key
- ShortUrlId      uniqueidentifier not null, indexed (no FK — see decision below)
- ShortCodeValue  varchar(7)       not null
- ClickedAt       timestamptz      not null
- UserAgent       varchar(512)     null
- IpAddress       varchar(45)      null
```

```csharp
public sealed class ClickAuditConfiguration : IEntityTypeConfiguration<ClickAudit>
{
    public void Configure(EntityTypeBuilder<ClickAudit> builder)
    {
        builder.ToTable("ClickAudits");

        builder.HasKey(c => c.Id);

        builder.Property(c => c.ShortUrlId).IsRequired();
        builder.HasIndex(c => c.ShortUrlId);

        builder.Property(c => c.ShortCodeValue)
            .HasMaxLength(7)
            .IsRequired();

        builder.Property(c => c.ClickedAt).IsRequired();
        builder.Property(c => c.UserAgent).HasMaxLength(512);
        builder.Property(c => c.IpAddress).HasMaxLength(45);
    }
}
```

**Decisions:**
- **No foreign key to `ShortUrls.Id`.** Audit log must survive deletion of its parent. If a `ShortUrl` is deleted, its `ClickAudit` rows remain as historical record. We index `ShortUrlId` for lookup but enforce referential integrity at the application level (we never delete `ShortUrls` in this version anyway).
- **`ShortCodeValue` denormalized.** Repeats data from the `ShortUrls` row. Phase 1 baked this into the entity; we honor it because audit queries often want the code without joining.
- **`ClickAudit` private constructor:** EF Core uses it reflectively. Same as `ShortUrl`.

### 3.4 `EfShortUrlRepository`

Concrete implementation of `IShortUrlRepository` from Phase 2.

```csharp
public sealed class EfShortUrlRepository : IShortUrlRepository
{
    private readonly ApplicationDbContext _db;

    public EfShortUrlRepository(ApplicationDbContext db)
    {
        _db = db;
    }

    public Task<ShortUrl?> GetByIdAsync(Guid id, CancellationToken ct) =>
        _db.ShortUrls.FirstOrDefaultAsync(s => s.Id == id, ct);

    public Task<ShortUrl?> GetByCodeAsync(ShortCode code, CancellationToken ct) =>
        _db.ShortUrls.FirstOrDefaultAsync(s => s.ShortCode == code, ct);

    public async Task<bool> ExistsByCodeAsync(ShortCode code, CancellationToken ct) =>
        await _db.ShortUrls.AnyAsync(s => s.ShortCode == code, ct);

    public Task AddAsync(ShortUrl shortUrl, CancellationToken ct)
    {
        _db.ShortUrls.Add(shortUrl);
        return Task.CompletedTask;
    }

    public Task UpdateAsync(ShortUrl shortUrl, CancellationToken ct)
    {
        // EF tracks the entity from GetBy*Async; no explicit Update needed
        // for the simple aggregate. Leaving as no-op here makes the Application
        // layer's intent explicit ("I am updating") and keeps a hook for future
        // detached-entity scenarios.
        return Task.CompletedTask;
    }

    public Task SaveChangesAsync(CancellationToken ct) =>
        _db.SaveChangesAsync(ct);
}
```

**Decisions:**
- **`UpdateAsync` is a no-op.** The `RedirectUseCase` flow loads the entity via `GetByCodeAsync` (which tracks it), mutates it (`RegisterClick`), then calls `UpdateAsync` followed by `SaveChangesAsync`. EF Core's change tracker already knows the entity is dirty; calling `_db.Update()` on a tracked entity is redundant and can cause "attempting to attach already attached entity" errors. The use case still calls `UpdateAsync` for intent clarity, and the no-op is documented.
- **Async wrapping:** `AddAsync` and `UpdateAsync` are sync underneath but exposed as `Task` to honor the interface. No fake-async with `Task.FromResult`; just `Task.CompletedTask`.
- **Equality on `ShortCode`:** the value object has structural equality (Phase 1), so the LINQ comparison `s.ShortCode == code` translates correctly via the `HasConversion`.

### 4.2 `Base62ShortCodeGenerator`

```csharp
public sealed class Base62ShortCodeGenerator : IShortCodeGenerator
{
    private const string Alphabet =
        "0123456789ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz";
    private const int CodeLength = 7;

    public Task<ShortCode> GenerateAsync(CancellationToken ct)
    {
        ct.ThrowIfCancellationRequested();

        Span<byte> bytes = stackalloc byte[CodeLength];
        RandomNumberGenerator.Fill(bytes);

        Span<char> chars = stackalloc char[CodeLength];
        for (var i = 0; i < CodeLength; i++)
        {
            chars[i] = Alphabet[bytes[i] % Alphabet.Length];
        }

        return Task.FromResult(ShortCode.Create(new string(chars)));
    }
}
```

**Decisions:**
- **`RandomNumberGenerator.Fill`** is the modern crypto-RNG API in .NET. Faster than `RandomNumberGenerator.Create()` per call.
- **`stackalloc`** for both byte and char buffers. Zero heap allocation per generation (other than the final `string` and `ShortCode` instance). Premature optimization? No — generators are called on every short URL creation, this is hot path.
- **Modulo bias:** `bytes[i] % 62` is technically slightly biased toward lower characters (256 % 62 = 8 → first 8 chars are 1 unit more likely than last 54). Acceptable for a 7-char URL slug; the bias is statistically invisible in practice. If we ever ship this for crypto-sensitive code generation we'd use rejection sampling; for URL slugs, it's a non-issue.
- **Returns `ShortCode` value object.** Validates via factory, defensive against an alphabet mistake.

### 4.3 `IDomainEventHandler<TEvent>` and `DomainEventDispatcher`

```csharp
public interface IDomainEventHandler<in TEvent> where TEvent : IDomainEvent
{
    Task HandleAsync(TEvent @event, CancellationToken ct);
}

public sealed class DomainEventDispatcher : IDomainEventDispatcher
{
    private readonly IServiceProvider _serviceProvider;

    public DomainEventDispatcher(IServiceProvider serviceProvider)
    {
        _serviceProvider = serviceProvider;
    }

    public async Task DispatchAsync(IEnumerable<IDomainEvent> events, CancellationToken ct)
    {
        foreach (var @event in events)
        {
            var handlerType = typeof(IDomainEventHandler<>).MakeGenericType(@event.GetType());
            var handlers = _serviceProvider.GetServices(handlerType);

            foreach (var handler in handlers)
            {
                if (handler is null) continue;

                var method = handlerType.GetMethod("HandleAsync")!;
                var task = (Task)method.Invoke(handler, new object[] { @event, ct })!;
                await task.ConfigureAwait(false);
            }
        }
    }
}
```

**Decisions:**
- **`IDomainEventHandler<TEvent>` is defined in Infrastructure**, not in Domain or Application. Reason: it's a dispatch contract for the dispatcher implementation, not a domain abstraction. Keeping it in Infrastructure prevents Application from coupling to dispatch mechanics.
- **Reflection-based invocation.** Necessary because `events` is `IEnumerable<IDomainEvent>` and we need to resolve the closed generic handler type per event runtime type. The cost is one `MakeGenericType` and one `GetMethod` per event; not free, but called at most a handful of times per request.
- **`GetServices` returns `IEnumerable`.** Multiple handlers per event are supported. For Phase 3 we have one handler (`ShortUrlClickedEventHandler`); the design admits more.
- **Sequential execution.** Handlers run one after another, not in parallel. Order is undefined (DI registration order, generally). If order matters, that's a separate concern not addressed here.
- **No retry, no error swallowing.** Handler exceptions propagate. Phase 2 dispatcher contract says: "if dispatcher throws after save, events are lost; this is acceptable for now."

### 4.4 `ShortUrlClickedEventHandler`

```csharp
public sealed class ShortUrlClickedEventHandler : IDomainEventHandler<ShortUrlClickedEvent>
{
    private readonly ApplicationDbContext _db;

    public ShortUrlClickedEventHandler(ApplicationDbContext db)
    {
        _db = db;
    }

    public async Task HandleAsync(ShortUrlClickedEvent @event, CancellationToken ct)
    {
        var audit = ClickAudit.Create(
            shortUrlId:     @event.ShortUrlId,
            shortCodeValue: @event.ShortCodeValue,
            clickedAt:      @event.ClickedAt,
            userAgent:      @event.UserAgent,
            ipAddress:      @event.IpAddress);

        _db.ClickAudits.Add(audit);
        await _db.SaveChangesAsync(ct);
    }
}
```

**Decisions:**
- **Separate `SaveChangesAsync`.** The handler runs after the use case's save. This is a second transaction. **Trade-off:** if this save fails, we have a click registered on `ShortUrls` (incrementing `ClickCount`) but no audit row. That's the at-most-once delivery limitation we accepted in Phase 2.
- **No outbox pattern.** Spec for Phase 2 noted this would land in a later phase if event durability becomes a requirement. For Phase 3, click audit loss on dispatcher failure is acceptable; the click count itself is preserved.
- **DbContext is scoped.** Handler shares the same `DbContext` instance as the repository for the request (per DI scope), but writes a separate change set after the repository's `SaveChangesAsync`.

## 5. AddInfrastructure Extension

```csharp
public static class InfrastructureServiceCollectionExtensions
{
    public static IServiceCollection AddInfrastructure(
        this IServiceCollection services,
        string connectionString)
    {
        services.AddDbContext<ApplicationDbContext>(options =>
            options.UseNpgsql(connectionString));

        services.AddScoped<IShortUrlRepository, EfShortUrlRepository>();
        services.AddSingleton<IShortCodeGenerator, Base62ShortCodeGenerator>();
        services.AddSingleton<IDateTimeProvider, SystemDateTimeProvider>();
        services.AddScoped<IDomainEventDispatcher, DomainEventDispatcher>();

        services.AddScoped<
            IDomainEventHandler<ShortUrlClickedEvent>,
            ShortUrlClickedEventHandler>();

        return services;
    }
}
```

**Decisions:**
- **`UseNpgsql`** as the productive provider. Tests substitute SQLite via a separate `AddInfrastructureForTesting()` helper or by overriding the registration in a fixture. Phase 3 ships `AddInfrastructure` for production wiring; the test fixture wires SQLite directly without going through this extension.
- **Service lifetimes:**
  - `DbContext`: scoped (EF default, one per request)
  - `EfShortUrlRepository`: scoped (depends on scoped DbContext)
  - `Base62ShortCodeGenerator`: singleton (stateless, thread-safe via crypto RNG)
  - `SystemDateTimeProvider`: singleton (stateless trivially)
  - `DomainEventDispatcher`: scoped (depends on scoped IServiceProvider for handler resolution)
  - `ShortUrlClickedEventHandler`: scoped (depends on scoped DbContext)
- **`connectionString` as parameter** instead of reading from `IConfiguration` here. Phase 4 will read config and pass the string. This keeps Infrastructure testable without a config provider.

## 6. Admin Use Cases (Application layer extension)

These three use cases land in `UrlShortener.Application`, not in Infrastructure. They were deferred from Phase 2 because integration tests needed real persistence to be meaningful. Now that Phase 3 ships persistence, they're actionable.

### 6.1 `DisableShortUrlUseCase`

**Request/Response:**

```csharp
public sealed record DisableShortUrlRequest(string Code);
public sealed record DisableShortUrlResponse(string Code, bool IsEnabled);
```

**Collaborators:** `IShortUrlRepository`, `IDomainEventDispatcher`.

**Algorithm:**

1. Build `ShortCode` via `ShortCode.Create(request.Code)`.
   - Catch `InvalidShortCodeException ex` → `return Errors.ShortCode.Invalid(ex.Message);`
2. `var shortUrl = await _repo.GetByCodeAsync(shortCode, ct);`
   - If `null` → `return Errors.ShortUrl.NotFound;`
3. `shortUrl.Disable();` (idempotent per Phase 1 refactor)
4. `await _repo.UpdateAsync(shortUrl, ct);`
5. `await _repo.SaveChangesAsync(ct);`
6. `await _dispatcher.DispatchAsync(shortUrl.DomainEvents, ct);`
7. `shortUrl.ClearDomainEvents();`
8. Return `new DisableShortUrlResponse(shortUrl.ShortCode.ToString(), shortUrl.IsEnabled);`

### 6.3 `UpdateExpirationUseCase`

**Request/Response:**

```csharp
public sealed record UpdateExpirationRequest(string Code, DateTime? NewExpiresAt);
public sealed record UpdateExpirationResponse(string Code, DateTime? ExpiresAt);
```

**Collaborators:** `IShortUrlRepository`, `IDomainEventDispatcher`.

**Algorithm:**

1. Build `ShortCode`.
   - Catch `InvalidShortCodeException ex` → `return Errors.ShortCode.Invalid(ex.Message);`
2. `var shortUrl = await _repo.GetByCodeAsync(shortCode, ct);`
   - If `null` → `return Errors.ShortUrl.NotFound;`
3. `try { shortUrl.UpdateExpiration(request.NewExpiresAt); }`
   - `catch (DomainException ex)` → `return Errors.Validation.InvalidExpiration(ex.Message);`
4. `await _repo.UpdateAsync(shortUrl, ct);`
5. `await _repo.SaveChangesAsync(ct);`
6. `await _dispatcher.DispatchAsync(shortUrl.DomainEvents, ct);`
7. `shortUrl.ClearDomainEvents();`
8. Return `new UpdateExpirationResponse(shortUrl.ShortCode.ToString(), shortUrl.ExpiresAt);`

> **Note:** these admin use cases produce no domain events in current Phase 1 design (`Disable`/`Enable`/`UpdateExpiration` don't raise). The dispatcher call with empty collection is preserved for uniformity, matching `CreateShortUrlUseCase` from Phase 2.

### 6.4 Constructor parameter ordering convention

For all use cases (existing and new), constructor parameters follow this order:

1. **Primary IO collaborators** (repository)
2. **Secondary IO collaborators** (generator, clock)
3. **Cross-cutting concerns** (dispatcher, future logger, etc.)

This standardizes new use cases and lets a future reviewer scan signatures with a predictable rhythm. **Existing Phase 2 use cases retain their current ordering** — refactoring would force test updates with no real value. The convention applies to the three admin use cases added in this phase.

## 7. Test Strategy — Phase 3

Phase 3 introduces two distinct test categories: **unit tests** (mock-based, sub-millisecond, like Phases 1-2) and **integration tests** (real DbContext + SQLite in-memory, ~10-50ms each).

### 7.1 SQLite in-memory fixture

```csharp
public sealed class SqliteInMemoryFixture : IDisposable
{
    private readonly SqliteConnection _connection;

    public SqliteInMemoryFixture()
    {
        _connection = new SqliteConnection("DataSource=:memory:");
        _connection.Open();

        Options = new DbContextOptionsBuilder<ApplicationDbContext>()
            .UseSqlite(_connection)
            .Options;

        using var ctx = new ApplicationDbContext(Options);
        ctx.Database.EnsureCreated();
    }

    public DbContextOptions<ApplicationDbContext> Options { get; }

    public ApplicationDbContext CreateContext() => new(Options);

    public void Dispose() => _connection.Dispose();
}
```

**Decisions:**
- **`SqliteConnection` opened explicitly and held open for the lifetime of the fixture.** SQLite's `:memory:` database vanishes when the connection closes; keeping one connection alive ensures the schema persists across multiple `DbContext` instantiations in the same test.
- **`EnsureCreated()`** instead of running migrations. Migrations are tested separately. For most repository tests, the schema-from-model approach is faster and avoids tying every repo test to migration state.
- **`CreateContext()`** returns a new `DbContext` per test action. Mimics the EF Core scoped lifetime in tests.
- **Per-test fixture, not class fixture.** Each test gets a fresh in-memory database. No cross-test contamination, no ordering dependency.

## 8. Migrations

### 8.1 Initial migration

The first migration is generated via:

```bash
dotnet ef migrations add InitialCreate \
    --project src/UrlShortener.Infrastructure \
    --startup-project src/UrlShortener.Infrastructure \
    --output-dir Persistence/Migrations
```

> **Startup project note:** Phase 3 has no Web host. EF Core CLI requires a startup project to construct the `DbContext`. Solution: Infrastructure project itself is configured to support design-time `DbContext` instantiation via an `IDesignTimeDbContextFactory<ApplicationDbContext>` implementation.

### 8.2 `DesignTimeDbContextFactory`

```csharp
public sealed class DesignTimeDbContextFactory : IDesignTimeDbContextFactory<ApplicationDbContext>
{
    public ApplicationDbContext CreateDbContext(string[] args)
    {
        var options = new DbContextOptionsBuilder<ApplicationDbContext>()
            .UseNpgsql("Host=localhost;Database=urlshortener_design;Username=postgres;Password=postgres")
            .Options;

        return new ApplicationDbContext(options);
    }
}
```

**Decisions:**
- The connection string here is a placeholder for design-time only. Migrations are generated against Npgsql conventions but never connect to the database during `migrations add`.
- File lives at `src/UrlShortener.Infrastructure/Persistence/DesignTimeDbContextFactory.cs`.
- Class is `internal sealed`. EF CLI discovers it via reflection regardless.

### 8.3 What gets committed

The generated files in `src/UrlShortener.Infrastructure/Persistence/Migrations/` are committed:

- `InitialCreate.cs` (the `Up`/`Down` methods)
- `InitialCreate.Designer.cs` (snapshot of the model at this migration)
- `ApplicationDbContextModelSnapshot.cs` (full current snapshot)

**Do not** commit any `.sql` files generated from `dotnet ef migrations script`. Those are deployment artifacts, not source.

## 10. What NOT to Do in Phase 3

- **Do not** modify Phase 1 Domain code. If something in Domain looks wrong, raise it as a question and stop. Do not edit silently. **Specifically, do not add a parameterless private constructor to `ShortUrl` or `ClickAudit` unless EF Core fails to materialize them — in which case stop and ask.**
- **Do not** modify existing Phase 2 Application code (`CreateShortUrlUseCase`, `RedirectUseCase`, `GetShortUrlUseCase`, `Result`, `Error`, `Errors`, etc.). Only add the three new admin use cases.
- **Do not** add multi-tenancy, soft delete, audit fields (`UpdatedBy`, `UpdatedAt`) to entities.
- **Do not** add an outbox pattern for domain event durability. Spec section 4.4 noted this would land later if needed.
- **Do not** add caching (memory, Redis, distributed) anywhere.
- **Do not** add logging (`ILogger`). Logging cross-cuts will be added in Phase 4 at the API edge.
- **Do not** add health checks, metrics, OpenTelemetry, or other observability. Phase 4 or later.
- **Do not** add API endpoints, controllers, Minimal API routes, ASP.NET Core, or any HTTP-related code. That is Phase 4.
- **Do not** add MediatR, FluentValidation, AutoMapper, Mapster, or any framework not on the allowed list.
- **Do not** add NuGet packages outside the allowed list:
  - `UrlShortener.Infrastructure`:
    - `Microsoft.EntityFrameworkCore`
    - `Microsoft.EntityFrameworkCore.Relational`
    - `Microsoft.EntityFrameworkCore.Design`
    - `Npgsql.EntityFrameworkCore.PostgreSQL`
    - `Microsoft.Extensions.DependencyInjection.Abstractions`
  - `UrlShortener.Infrastructure.Tests`:
    - `xunit`, `xunit.runner.visualstudio`, `Microsoft.NET.Test.Sdk`
    - `FluentAssertions`, `Moq`, `coverlet.collector`
    - `Microsoft.EntityFrameworkCore.Sqlite`
    - `Microsoft.Data.Sqlite`
    - `Microsoft.Extensions.DependencyInjection` (concrete impl, needed for ServiceCollection in DI tests — same as Phase 2)
- **Do not** ship raw SQL migration scripts. Use EF migrations.
- **Do not** allow domain exceptions to escape any use case method. Phase 2 contract preserved.
- **Do not** modify the `connectionString` parameter of `AddInfrastructure` to read from `IConfiguration`. Phase 4 owns config.
- **Do not** parallelize handler invocation in `DomainEventDispatcher`. Sequential per spec section 4.3.
- **Do not** swallow handler exceptions. They propagate.
- **Do not** add seed data, demo records, or any fixed `INSERT` in migrations.
